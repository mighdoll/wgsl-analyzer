The result id is a fingerprint, not a stored token

crates/wgsl-analyzer/src/diagnostics/result_id.rs:53 · hunk from line 53

The id is recomputed from the diagnostics on every pull, so the server stores nothing between pulls. stated

  • Hashes the converted lsp_types::Diagnostic list (ranges after line-index conversion, related info, tags), so it changes exactly when what the client sees changes. stated
  • DefaultHasher::new() has fixed keys, so ids are stable within a process. The doc explains why not FxHasher (a collision leaves stale diagnostics). stated
  • The open flag rationale (result_id.rs:38) assumes the client sends its last workspace id after a close. That is 9.0.1 behavior; 10.1.2 sends none (see Where to focus). inferred new this run
  • Tests: result_id.rs:164 (open flag), result_id.rs:180 (each visible field changes the id).
pub(crate) fn result_id(
    items: &[Diagnostic],
    open: bool,
) -> Option<String> {
    if items.is_empty() {
        return None;
    }
    let mut hasher = DefaultHasher::new();
    items.hash(&mut hasher);
    open.hash(&mut hasher);
    Some(format!("{:016x}", hasher.finish()))
}

Read it this way: items.is_empty() -> a clean file has no id; open.hash -> open and closed ids differ.

Streaming: only new diagnostics go out early

crates/wgsl-analyzer/src/diagnostics/workspace_report.rs:235 · routing workspace_report.rs:104 · sender lsp/utilities.rs:67 · hunk from line 235

A full entry with an id is buffered and flushed as a $/progress chunk once the interval has passed. Everything else waits for the response. stated

  • FlushPolicy::SERVER is Interval(50 ms) (workspace_report.rs:195). Tests use a Count policy so they never read the clock, and no test streams with SERVER. stated
  • maybe_flush also runs after clean files, so a buffered entry does not wait for the next new one. stated
  • Chunks go straight onto the connection from the worker. The response goes through the main loop after the handler returns, so chunks always arrive first (doc at utilities.rs:63). stated
  • Every chunk is typed WorkspaceDiagnosticReportPartialResult. The spec's first-chunk type has the same wire shape (test workspace_report.rs:662). stated
  • sent_chunk is the flag long polling reads in stop 7. stated
fn maybe_flush(&mut self) {
    if self.unsent.is_empty() {
        return;
    }
    let due = match self.policy {
        FlushPolicy::Interval(interval) => self.last_flush.elapsed() >= interval,
        #[cfg(test)]
        FlushPolicy::Count(count) => self.unsent.len() >= count,
    };
    if due {
        let items = mem::take(&mut self.unsent);
        self.sender
            .send(WorkspaceDiagnosticReportPartialResult { items });
        self.last_flush = Instant::now();
        self.sent_chunk = true;
    }
}

The parked-request slot and its counter

crates/wgsl-analyzer/src/long_poll.rs:99 · module doc long_poll.rs:1 · hunk from line 99

At most one request is parked. The counter counts wakes, whether or not anything was parked. stated

  • park compares the count taken at dispatch with the current one. A handler that ran across a change would park a stale "nothing changed", so it runs again at once. stated
  • A second parked request displaces the first, which is answered with its empty report. stated
  • Why a counter, not the salsa revision: opening or closing a file changes the id (the open flag) without moving the revision. stated (journal)
  • Unit tests: long_poll.rs:163 (ran across a change), long_poll.rs:175 (displacement).
pub(crate) fn park(
    &mut self,
    suspended: Suspended,
) -> Park {
    if suspended.changes != self.changes {
        return Park::RunAgain(suspended.request);
    }
    match self.parked.replace(suspended) {
        Some(displaced) => Park::Displaced(displaced.no_news),
        None => Park::Parked,
    }
}

pub(crate) fn wake(&mut self) -> Option<Request> {
    self.changes += 1;
    self.parked.take().map(|parked| parked.request)
}

1. Closing a file within 2 s of a workspace answer can strand its diagnostics (10.1.2) inferred new this run

vscode-languageclient 10.1.2 forgetDocument also forgets the file's workspace result id on close; 9.0.1 kept it. See vscode-languageclient@10.1.2 lib/common/diagnostic.js:287 (this.forget(PullState.workspace, document)), absent from 9.0.1's forgetDocument.

When a pull is parked at the close, its earlier previousResultIds still carry the id, and the wake clears or refreshes the file. In the 2 s gap after an answer, nothing is parked. The next pull sends no id, and the server omits a clean file (workspace_report.rs:307) and does not check a closed library file (global_state.rs:682).

Result: errors from the last pre-close document pull stay in the Problems panel. Two paths: "Don't Save" on a file that is clean on disk, and a dependency file opened by go to definition. The second is the bug commit 6235a776 fixed.

Guard: none. No test models the client, and manual check step 8 (workspace-diagnostics-manual-check.md:65) waits for the pull to park before closing. Try it first, step 6, reproduces it.

2. The final response after chunks is not empty stated

This was a major item in the earlier review. finish puts unchanged, cleared, and unsent full entries in the response after chunks went out. LSP 3.17's general rule says that response carries no results. ty does the same. Both 9.0.1 and 10.1.2 apply the response's entries (10.1.2 read this run).

A client that follows the spec would drop the cleared entries and keep stale diagnostics. Documented as a departure in diagnostics.md:31.

Guarded: current behavior pinned by pull_diagnostics.rs:690. Conforming (send the rest as a final chunk, answer {items: []}) is a few lines in workspace_report.rs:155.

3. Every change re-checks the whole workspace while a pull is parked stated

Each wake (main_loop.rs:549) re-runs the full check. Journal numbers, release build: 370 ms re-check and 592 ms after a one-file edit on an 11 MB .wgsl corpus; 3.3 ms and 18 ms on bevy's .wesl. naga output is not cached per file.

The next keystroke usually cancels the run: a ServerCancelled answer, then a client re-pull 2 s later. Still a large net win over re-checking every 2 s.

Guard: none, no perf test. Options: debounce the wake, skip when the salsa revision did not move (misses open/close), memoize naga per file.

4. As-you-type diagnostics depend on the server's refresh under 10.1.2 inferred new this run

10.1.2 changed the default diagnosticPullOptions to onChange: false (9.0.1 defaulted to true), and editors/code sets none. Open documents are re-pulled when the server sends workspace/diagnostic/refresh, which it does on every state change (main_loop.rs:533, pre-existing).

The workspace answer does not help here: the client skips workspace entries for files it tracks by document pull. So the earlier review's "stop sending refresh?" option would freeze open files' diagnostics while typing.

Guard: none. The harness runs with refresh off.

5. One empty diagnostic message fails the whole workspace response stated

The push path patches "" to " " (global_state.rs:529); the pull converter (request.rs:511) does not. 10.1.2 converts chunk entries inside a try/catch but response entries without one, so a bad entry in the response fails the pull and counts toward the six-failure cutoff. No known producer.

Guard: none. Moving the patch into the shared converter is cheap.

6. Chunks can follow a RequestCancelled answer stated

handle_cancel drops the parked request and answers at once (notification.rs:39); a running worker keeps streaming (utilities.rs:85). VS Code drops progress for a disposed token.

Guard: none; no streaming test goes through the main loop.

7. The "Don't Save" race is narrowed, not closed stated

The open flag (result_id.rs:38) fixes the usual case; the fixed case is guarded by pull_diagnostics.rs:579. Its reasoning assumes 9.0.1's close behavior, so card 1 changes the analysis under 10.1.2.

8. URI spelling differs by entry kind stated

Full and unchanged entries use the server's URI; cleared entries use the client's. Two client spellings of one file: the later wins, the earlier gets no answer (workspace_report.rs:60). VS Code normalizes, so it never sees either case. No test.

9. Pulls before quiescence inferred

The pull gate checks only vfs_done (dispatch.rs:284). During package re-discovery a pull computes against the old package graph and may answer import errors that the pull after quiescence corrects. Self-correcting, no panic. No test.

Quiz

Answer out loud before you click. Hardest decisions first.

A pull that streamed a chunk is always answered, even when every other entry is unchanged. Why not park it?

Run again, it would compare against the previousResultIds it was sent with, which lack the ids the client took from the chunks. A streamed file fixed in between would then be omitted instead of cleared, and its errors would stick. stated workspace_report.rs:172

Why hash "is the file open" into the result id, and what does it cost?

In 9.0.1, VS Code sends the document pull's id while a file is open and its last workspace id after it closes. Without the flag, a "Don't Save" close could match an id learned while the file was open, get "unchanged", and hide the on-disk errors.

  • Cost: one redundant full report per close of a file with diagnostics.
  • Follow-up: 10.1.2 sends no id after a close; what breaks then? (Card 1.)
  • result_id.rs:38
What goes wrong without the wake counter, and why not use the salsa revision instead?

A handler that started before a change and finished after would park a "nothing changed" computed from an old snapshot. It would then wait for the change after the one it missed.

  • Opening or closing a file changes the id without moving the revision, so the revision would miss those.
  • long_poll.rs:103, test pull_diagnostics.rs:814
Why give a clean file no id, rather than the id of an empty list?

So the workspace pull can tell a fixed file (the client still sends an id -> cleared entry) from a file that never had diagnostics (no id -> omitted). The cost is an empty full report where "unchanged" would do. stated (commit 9418af8a)

Why does finish leave an unclaimed id alone while its file is open?

VS Code keeps sending the document pull's id for an open file the workspace pull skips (say, a WGSL-mode file without a shader extension). Clearing it would put a cleared entry in every pull, so no pull would ever suspend. workspace_report.rs:168

Why key previous ids by FileId rather than the URI string, and what does that cost?

The server's file_id_to_url need not spell a URI the way the client did. The cost: two client spellings of one file collapse, the later wins and the earlier gets no answer. workspace_report.rs:88

Why record line endings after apply_change instead of under the VFS lock before it?

Snapshots share the live VFS. apply_change blocks until every older snapshot drops, so anything recorded after it is visible only to snapshots whose database has the file.

  • has_text relies on that to avoid panics in file_source_root and file_line_index.
  • global_state.rs:315
A displaced or shut-down parked pull gets an empty report, not RequestCancelled. Why?

vscode-languageclient treats a RequestCancelled it did not ask for as a failed pull, and six failures stop workspace pulls for the session (same in 9.0.1 and 10.1.2). A client-initiated cancel is different: the client expects that error.

  • long_poll.rs:107 (Displaced), main_loop.rs:984 (shutdown)
